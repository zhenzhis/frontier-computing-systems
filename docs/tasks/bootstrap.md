# 正式管理与开源：首次建项

日期：2026-10-14；公开版本：0.1.0。

## 目标与授权

维护者要求先备份当前工作流与每个历史版本，再新建正式项目目录并推送公开 GitHub。部署对象是新的源码仓库；没有更改正在运行的模型、认证、Magpie 路由或 Pi 配置。

## 验收与证据

- 原始历史：全部 8 个提交、全 refs Git bundle、原样版本归档保存于私人加密快照。
- 当前私人快照：3050 个文件；保存后重新解密全部 557 分块并验证完整 ZIP SHA-256。
- 公开源码：单独历史、MIT 许可、上游署名、固定依赖、清单、中文维护手册和研究摘要。
- 本地验证：39 个实际测试用例；真实 Pi SDK 加载 5 个命令、6 个提示、1 个 Skill，并调用 2 个只读状态命令；Windows 权限适配器加载成功，没有模型请求。
- 源码恢复：测试创建两个版本和 tag，备份全部历史，在新目录 clone bundle 并核对 HEAD、tag 与文件字节；真实公开项目发布前也核对自己的 bundle。
- 远程证据：每次提交对应的 [GitHub Actions](https://github.com/zhenzhis/zhenzhi-workflow/actions/workflows/verify.yml)；推送与 CI 的实时状态以该页为准。

## 修复与限制

首次私有 ZIP 超过 MemoryStream 可支持长度，改为磁盘 ZIP 与 4MiB DPAPI 分块，再验证保存后的归档。移植时发现上游权限包根入口是服务 API，改为固定版本的 Pi 扩展入口；SDK 检查补上 shutdown 生命周期，避免测试进程残留。恢复测试明确 LF 属性，避免 Windows Git 的换行转换掩盖文件字节差异。

私人快照可解密并不等于外部 Provider 和服务已运行恢复。SDK 禁网加载不等于付费模型、订阅、所有终端视觉或所有危险命令已验证。模式审计会漏掉未知形式的秘密，所以仍需审查 diff 和公开历史。

## 后续维护

采用这个仓库管理新源码迭代，按 maintenance 中的版本流程备份、验证和发布。活动配置迁移、意图分流、持续自动维护和生产适配器分别作为有验收与授权的后续工作。
