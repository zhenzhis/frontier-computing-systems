# 模型职责与性能评估

当前采用手动选择模型。按照任务职责分组，而不是用一份综合排行榜推导所有用途的最优解。

| 职责 | 候选所需能力 | 验证方式 |
|---|---|---|
| 需求、架构、未知原因调试 | 推理、约束遵循、跨文件整合 | 实际项目难例、验收与返工 |
| 有界实施 | 工具稳定性、代码修改、指令遵循 | 指定文件回归与接口验收 |
| 检索、整理、反馈筛选 | 信息抽取、拒判、结构化输出 | 已标注样本及困难负例 |
| UI 与视觉审查 | 图片读取、空间理解、交互判断 | 实际截图与人工验收 |
| 独立审查 | 反例发现、不同证据或方法 | 实际 diff、可信检查与复现 |

模型元数据和上下文容量只描述接口。对每个实际端点验证工具调用、图片、结构化输出、努力等级、限流和恢复，再做项目能力测试。第一 token 延迟和峰值 tokens/s 都不能代替交付成功率。

保留输出与工具预算；目标、约束、验收和未决失败在上下文中突出。192K 提醒是可调试用起点。不同模型的最佳长度需要用多位置证据检索、跨文件追踪、约束保持与恢复测试确认，单次捞针成功不等于复杂开发注意力没有衰减。

升级看证据：范围扩大、验收失败、来源冲突、工具/视觉不兼容或重复复现失败。先保留失败和状态，再切换强角色；不能依赖可用性 fallback 自动修复语义错误。
