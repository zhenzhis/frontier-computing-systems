# FCS 测试、评估与研究方法

日期：2026-10-17。状态：方法研究与工程协议已实现；真实模型对照和维护者体验研究尚未执行。具体离线检查结果由当前命令输出与私有回执承载，本文件不发布个人部署信息。

## 问题与假设

问题：如何知道 FCS 的优化提高了真实任务交付与实际使用体验，而不只是提高测试通过数、解释流畅度或公开榜单分数？

区分三个主张：工程行为正确、受控任务能力改善、使用者取得净收益。它们需要不同证据。当前可确认的是新版证据约束的工程行为；待测假设是：经核实的失败尝试信息，相较现有恢复或等量其他有用上下文，能改善恢复后正确率且成本可接受。

预测可被反驳：若相同预算和任务分布下收益消失、重复错误不减少、误导与返工增加，或总成本超过预定容忍范围，就拒绝或暂缓该候选。停止条件与预算在确认性试验之前冻结。

## 结果与证据：分层评估矩阵

| 层次 | 要回答的问题 | 结果与检查 | 不能推出什么 |
|---|---|---|---|
| 工程与对抗回归 | 所声明边界是否成立？ | 版本漂移、假成功、工件变化、重复/缺失、崩溃恢复和预算检查 | 真实模型更聪明、真实用户更省心 |
| 公共基准 | 在固定外部任务集表现如何？ | 固定模型+Harness+预算+任务版本的任务通过、成本/质量曲线 | 对自己的项目一定有收益；与不同脚手架的榜分直接可比 |
| 私有代表性任务 | 本工作流在哪些任务改善？ | 隐藏最终集、真实产物、配对结果、任务族分层、全部尝试 | 对所有软件任务或研究问题普遍更优 |
| 受控机制研究 | 哪项信息/机制产生变化？ | 单变量、消融、等预算主动对照、反例和干预 | 观察到相关就证明原因 |
| 独立验收与复现 | 结果是否依赖开发者的解释？ | 候选外的可信评分器；未参与调优的评审者复核；重要结果另环境复现 | 同一 Agent 再审一次就成为独立研究 |
| 实际使用体验 | 成本、干预、可理解性是否值得？ | 维护者完成真实任务，计时、返工、干预及体验记录 | Agent 代填评分；仅凭感觉宣称生产力提升 |

### 评分器与基准校准

先让已知正确解通过，让空操作、格式正确但事实错误、改错对象、只写成功声明和绕过必要约束的近邻解失败。公开题目也要复核：任务可解、提示与验收一致、依赖可得、随机性可控。保持所有校准失败记录。任务构建者和评分器构建者可能共享盲点，重要结论需独立复核。

模型裁判用于难以程序判定的质量部分：隐藏条件标签，随机交换输出顺序，用参考和人工标注校准，报告分歧及位置偏差；使用另一模型也不自动获得独立真值。真实性、授权和产物存在等硬项尽量程序验证。评分器改动后明确重评分版本，不挑选对候选更有利的评分器。

任务集版本化：改变任务/可用工具/资源时重跑；只修验收且产物充分时可重新评分；不影响测量的元数据可复用。保留旧回执、任务版本和变更原因。已被反复查看的公开或私有最终题不能继续充当未见确认集。

### 指标与统计

主要指标：实际任务成功率。并列报告有效失败、无效试验、硬约束违规、端到端时间（含检查与返工）、执行时间、成本、Token、人工干预与恢复错误。成本质量图保留原始分量；不把不同性质的风险折成一个总分。

pass@k 问的是有限尝试中至少成功一次；pass^k 问的是连续 k 次均成功的可靠性；前者增加重试通常会改善，不能据此宣称稳定。小样本直接报告每题各次结果、全重复通过的任务数和 k；当前 v2 的 allRepeatsPassedTasks 是观测计数，不冒称总体 pass^k 估计器。

按相同任务与初始状态配对，随机或交错执行条件，固定预算与环境，计入选择/搜索成本；若测试时服务版本变化，记录为不同条件。按任务族聚类，任务改写和重复不增加独立 n。确认前声明主指标、效果阈值、成本/时间容忍、重复次数、缺失与重试规则；探索阶段可以换解释，确认阶段不能边看结果边改计划。多候选先在选择集确定一个，再进入最终集；多终点或多候选的确认需处理多重比较。

当前工程门禁使用保守单侧 Hoeffding 下界，并明确独立代表性抽样假设；它不是通用最优统计方法。18 题先导实验只定位流程问题与方向，不应据此强推正式采纳；通过预先声明的条件也仍需人工复核。正式研究依据任务变异、最小有价值效应和成本做样本量/功效规划，再预注册分析方法。

## 决定与下一步

### 首个有限研究：恢复信息 A/B/C

A 为当前恢复；B 为 A 加经核实的失败尝试和解释状态；C 为 A 加等量其他有用的状态/约束/下一步信息。各臂的上下文、执行和信息获取预算相同。B-C 衡量失败信息相对另一种上下文用途的价值；不能把它解释为纯粹“原因解释”的效应，后者需另做消融。

18 题按任务族分为开发 6、选择 4、报告 8；开发和选择每臂每题一次，冻结后报告每臂每题两次，78 次总尝试；另留最多 22 次预定基础设施重试，总计 100。不得通过另建 id 绕过预算。当前 v2 不自动重试；模型适配器和重试槽位须在启动前冻结。真实调用须先确定模型、渠道和费用/Token 上限；此文件不启动费用。

### 实际体验验收

使用 [体验验收表](../../templates/体验验收.md)。先做公开的零模型演示，检查“能否发现错误、解释为何不通过、找到证据、决定下一步”。这是可用性走查，维护者体验评分仍待本人填写。

正式试用从维护者的真实待办中选取任务并记录全部入选/排除原因。按难度、熟悉度和任务类型配对；可行时采用交错/随机条件，避免总先做旧版再做新版。不要重复做同一已经学会的任务来制造速度提升；使用等难但不同任务或明确记录学习效应。输出质量可隐藏版本标签后盲评；交互工作流通常无法完全盲法，应注明。

同时记录维护者的主动工作时间、等待时间、返工、被要求确认次数、必要干预、任务最终正确性和 1–5 分体验。预先规定何时记录，不只挑最顺利的几次。低负担试用可以先收集少量配对任务以发现问题，但单一维护者的小样本仅支持个人适用性，不能宣称群体生产力效应。

最终决定可为采纳、有限试用、暂缓或拒绝。优先级：硬约束与证据真实 -> 任务质量 -> 总负担和费用 -> 主观偏好。硬约束不能被速度抵消；质量和费用的取舍由维护者在看最终集前确定。没有足够证据时停止扩张并保留未知项。
